# Research Release Checklist

This checklist is the publication and archive gate for a result. It does not
promote a simulation result to hardware evidence. Complete it for a specific
`run_id` after the experiment record, evaluation, and safety gates are
reviewed.

## Evidence bundle

- [ ] Research question, hypothesis, variables, baseline, and safety limits are
      stated in the experiment record.
- [ ] The exact Git commit, branch, YAML configuration, and environment lock
      are recorded in the run manifest.
- [ ] Training, validation, and test splits are episode-safe and their seeds
      are listed.
- [ ] Baselines, ablations, aggregate statistics, uncertainty intervals, and
      per-seed results are generated by versioned scripts.
- [ ] Failed episodes and negative or inconclusive results are retained.
- [ ] Figures and tables are generated from the archived metrics, and every
      equation uses the versioned observation/action/controller interface.
- [ ] The artifact manifest and SHA-256 checksums verify the archived copy on
      `/mnt/research-data`.

## Literature and claims

- [ ] Each claim has a dated source and a structured paper note.
- [ ] Publisher or authorized portal full text is distinguished from
      `metadata-only` discovery records.
- [ ] Limitations, unsupported conclusions, and missing hardware evidence are
      written next to the result rather than omitted.

## Hardware boundary

- [ ] No hardware command is enabled unless robot, sensor, limits, watchdog,
      emergency stop, operator, and rollback procedure are documented.
- [ ] Simulation-only results are labeled as simulation-only; sim-to-real and
      real-robot claims require calibration and offline replay evidence.

## Run handoff

Fill these fields in the experiment record or release note:

```text
run_id:
git_commit:
config:
environment_lock:
artifact_root:
archive_root: /mnt/research-data
evaluation_command:
figure_commands:
paper_note_paths:
known_limitations:
```

The checklist is a review aid. The automated checker validates only that this
contract and its referenced project gates exist; a human must mark each item
for the particular result.
